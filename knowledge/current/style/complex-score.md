# 软件系统动态熵增控制与质量评价体系

> **版本**: V1.0  
> **生效日期**: 2026-04-17  
> **适用范围**: 所有中大型长期维护的软件系统，特别适用于敏捷迭代开发模式  
> **本项目落地脚本**: `.opencode/scripts/harness/complexity-score.sh`

---

## 1. 体系概述

### 1.1 背景与目的

软件系统在持续迭代过程中，随着业务复杂度的增加，其无序程度（熵）会自发单调递增，
最终导致维护成本超过业务收益，系统走向崩溃。传统静态代码质量评价方法无法有效衡量
单次变更对系统整体复杂度的影响，也无法建立长期的质量控制机制。

本体系基于**信息熵理论**与 **Chidamber-Kemerer (CK) 度量集**，提出 **"delta-熵增"**
核心概念，将模糊的"代码质量"转化为可量化、可追踪、可控制的数值指标，实现对软件系统
全生命周期的动态质量管控。

### 1.2 核心目标

1. 量化单次变更带来的系统复杂度变化（delta-熵增）
2. 建立变更质量的客观评价标准，区分"好的变更"与"坏的变更"
3. 将质量控制嵌入软件开发生命周期的每个环节
4. 建立长期熵增治理机制，确保系统健康度维持在合理区间
5. 使系统熵增速度不超过业务价值增长速度

### 1.3 核心原则

| 原则 | 说明 |
|------|------|
| **不可避免性** | 接受总熵增的必然性，重点控制单位业务价值的熵增率 |
| **增量控制** | 关注变更前后的指标差值（delta），而非静态绝对值 |
| **全流程覆盖** | 从设计到发布的每个环节都进行熵增控制 |
| **权责对等** | 谁增加熵，谁负责偿还 |
| **适度** | 追求"恰到好处"的熵，而非绝对的零熵 |

## 2. 核心理论基础

### 2.1 软件熵的公理化定义

软件系统的熵 **S** 是系统无序程度、不确定性和认知复杂度的综合度量，满足以下公理：

1. **单调性公理**: 封闭软件系统的总熵随时间单调非递减 `dS/dt >= 0`
2. **可加性公理**: 系统总熵等于各子系统熵之和加上子系统间的关联熵
   `S_total = Σ S_i + S_coupling`
3. **delta 公理**: 任何变更都会产生熵增 `ΔS = S_after - S_before`，
   变更的质量由 ΔS 与业务价值 V 的比值决定

### 2.2 核心命题

- 无法阻止总熵增，但可以控制单位业务价值的熵增率 `r = ΔS / ΔV`
- 健康系统的必要条件是 `r <= r_threshold`，即熵增速度不超过业务价值增长速度
- 系统崩溃的临界点是 `dS/dt >> dV/dt`，此时维护成本超过业务收益

### 2.3 熵增的分类与来源

| 熵增类型 | 来源 | 可避免性 | 控制优先级 |
|----------|------|----------|-----------|
| **必要熵增** | 业务逻辑本身的复杂性 | 不可避免 | 接受 |
| **架构熵增** | 不合理的模块划分和依赖关系 | 可避免 | **最高** |
| **实现熵增** | 糟糕的代码质量和设计 | 可避免 | 高 |
| **运行时熵增** | 隐式依赖、数据不一致、故障传播 | 可避免 | 中 |
| **认知熵增** | 文档缺失、知识断层、团队认知不一致 | 可避免 | 高 |

## 3. 度量指标体系

### 3.1 符号体系约定

设软件系统为有向图 `G = (V, E)`，其中：

- `V = {C_1, C_2, ..., C_n}` — 系统中所有类的集合
- `E ⊆ V × V` — 类之间的依赖关系集合，`(C_i, C_j) ∈ E` 表示类 C_i 直接依赖 C_j

对任意类 `C ∈ V`：

- `M(C) = {m_1, m_2, ..., m_k}` — 类 C 的所有方法集合
- `F(C) = {f_1, f_2, ..., f_l}` — 类 C 的所有实例变量集合
- `Inherit(C)` — 类 C 直接继承的父类集合
- `Implement(C)` — 类 C 直接实现的接口集合

### 3.2 静态 delta-熵增度量（代码层面）

所有指标均计算变更前后的差值 `ΔX = X_after - X_before`。

#### 3.2.1 耦合度指标（度量模块间关联熵）

**CBO（对象间耦合度, Coupling Between Objects）**

```
CBO(C) = |{ C' ∈ V \ {C} | (C, C') ∈ E }|
```

- 依赖关系包括：成员变量类型、方法参数/返回值类型、实例化、方法调用、继承、实现、异常
- 排除 JDK 标准库类依赖
- **delta 阈值**: 优秀 ≤ 0 / 警告 ≤ 1 / 禁止 ≥ 2

**RFC（类的响应集, Response For a Class）**

```
RFC(C) = |M(C) ∪ ⋃_{m ∈ M(C)} calledMethods(m)|
```

- **delta 阈值**: 优秀 ≤ 2 / 警告 ≤ 5 / 禁止 ≥ 10

**CYCLE（循环依赖）**

```
CYCLE(G) = { <C_i1, ..., C_ik> | k >= 2, C_i1 = C_ik, ∀ 1<=j<k, (C_ij, C_{ij+1}) ∈ E }
```

- 危害度: `H(c) = |c|^2`（|c| 为环的长度）
- **规则**: 任何级别的循环依赖均**绝对禁止**
- 权重: 每个循环依赖的熵增贡献为 `10 × 危害度`

#### 3.2.2 内聚度指标（度量模块内部混乱熵）

**LCOM3（方法内聚缺乏度第 3 版, Lack of Cohesion of Methods v3）**

```
LCOM3(C) = 1 - (2 / k(k-1)) × Σ_{1<=i<j<=k} s(m_i, m_j)
```

其中相似度函数:

```
s(m_i, m_j) = 1  若 accessedFields(m_i) ∩ accessedFields(m_j) ≠ ∅
            = 0  否则
```

- 边界条件：若 `k <= 1`，则 `LCOM3(C) = 0`
- **delta 阈值**: 优秀 ≤ 0 / 警告 ≤ 0.5 / 禁止 ≥ 1

**WMC（类的加权方法数, Weighted Methods per Class）**

```
WMC(C) = Σ_{m ∈ M(C)} CC(m)
```

其中圈复杂度 `CC(m) = 1 + numberOfBranches(m)`

- **delta 阈值**: 优秀 ≤ 5 / 警告 ≤ 10 / 禁止 ≥ 20

#### 3.2.3 继承体系指标（度量传递熵）

**DIT（继承树深度, Depth of Inheritance Tree）**

```
DIT(C) = 0                                           若 C = Object
       = 1 + max{ DIT(C') | C' ∈ Inherit(C) }       否则
```

- **delta 阈值**: 优秀 ≤ 0 / 警告 ≤ 1 / 禁止 ≥ 2

**NOC（子类数量, Number of Children）**

```
NOC(C) = |{ C' ∈ V | C ∈ Inherit(C') }|
```

- **delta 阈值**: 优秀 ≤ 0 / 警告 ≤ 1 / 禁止 ≥ 2

#### 3.2.4 综合静态 delta-熵增

```
ΔS_static = ΔS_c + ΔS_h + ΔS_i
```

其中：

- **耦合熵增**: `ΔS_c = ΔCBO + 0.2 × ΔRFC + ΔS_cycle`
- **内聚熵增**: `ΔS_h = 2 × ΔLCOM3 + 0.1 × ΔWMC`
- **继承熵增**: `ΔS_i = ΔDIT + 0.5 × ΔNOC`

### 3.3 动态 delta-熵增度量（运行时层面）

> **注**: 动态度量依赖 APM 工具和运行时数据，属于远期规划。

**运行时耦合熵增 ΔS_rc**

基于 APM 工具收集的调用链数据，计算每个模块实际入度和出度的变化。
重点检测静态分析无法发现的反射调用、事件总线依赖等隐式依赖。

**故障熵增 ΔS_f**

```
ΔS_f = 0.5 × ΔMTTR + 1 × ΔImpact + 2 × ΔCorrelation
```

- MTTR: 平均故障恢复时间
- Impact: 平均故障影响范围
- Correlation: 故障关联度

**数据熵增 ΔS_d**

```
ΔS_d = 0.1 × ΔFields + 1 × ΔRedundancy + 5 × ΔInconsistency
```

- Fields: 数据库表字段数量
- Redundancy: 数据冗余度
- Inconsistency: 数据一致性错误率

#### 3.3.1 综合动态 delta-熵增

```
ΔS_dynamic = ΔS_rc + ΔS_f + ΔS_d
```

### 3.4 变更质量评价指标

**熵增密度**: 单位业务价值带来的熵增

```
ρ = ΔS_total / ΔV
```

其中 ΔV 为本次变更带来的业务价值，采用功能点（FP）或故事点（SP）量化。

| 熵增密度 | 变更质量等级 | 处理策略 |
|---------|-------------|---------|
| ρ ≤ 0.1 | 优秀 | 正常通过 |
| 0.1 < ρ ≤ 0.5 | 可接受 | 正常通过，记录观察 |
| 0.5 < ρ ≤ 1 | 高风险 | 需要架构师审批 |
| ρ > 1 | 有害 | 拒绝变更 |

### 3.5 系统健康度评价

```
H(t) = 100 × (1 - S_total(t) / S_max)
```

其中：

- `S_total(t) = S_0 + Σ_{i=1}^{n(t)} ΔS_i` 为系统到时间 t 的总熵
- `S_max = 20 × |V|` 为系统最大可接受熵值（|V| 为系统类总数）

| 健康度 | 系统状态 | 应对策略 |
|--------|---------|---------|
| H ≥ 80 | 健康 | 正常开发，维持现有控制机制 |
| 60 ≤ H < 80 | 亚健康 | 加强熵增控制，增加重构比例 |
| 40 ≤ H < 60 | 不健康 | 暂停新功能开发，集中重构 |
| H < 40 | 病危 | 评估架构重写的必要性 |

## 4. 全生命周期 delta-熵增控制机制

### 4.1 设计阶段：熵增预评估

在需求分析和架构设计阶段，执行**架构影响评估（AIA）**流程：

1. **功能定位**: 确定新功能在现有架构中的最佳位置
2. **依赖分析**: 预测新增依赖的数量和类型
3. **熵增估算**: 根据历史数据估算本次变更的 ΔS
4. **价值对比**: 计算熵增密度 ρ，判断是否值得实施
5. **方案优化**: 如果 ρ 过高，重新设计方案降低熵增

设计原则：最小依赖原则、开闭原则、单一职责原则、可选依赖原则

### 4.2 编码阶段：实时熵增反馈

- **IDE 插件集成**: 安装 MetricsReloaded 等插件，实时计算当前编辑类的各项指标
- **增量分析**: 只分析本次修改的代码，提高反馈速度
- **智能提示**: 当指标超过阈值时，给出具体的优化建议
- **预提交检查**: 提交代码前自动运行 delta-熵增检查，阻止高熵增代码提交

### 4.3 审查阶段：熵增强制检查

将 delta-熵增指标作为代码审查的强制通过条件。

**代码审查熵增检查清单**：

- [ ] 本次变更的 ΔS_static 是否超过阈值？
- [ ] 是否引入了新的循环依赖？
- [ ] 是否破坏了现有模块的内聚性？
- [ ] 是否增加了不必要的耦合？
- [ ] 熵增密度 ρ 是否在可接受范围内？

**分级审批机制**：

| ΔS 范围 | 审批级别 |
|---------|---------|
| ΔS ≤ 2 | 普通开发者审查通过 |
| 2 < ΔS ≤ 5 | 资深开发者审查 |
| 5 < ΔS ≤ 10 | 架构师审查 |
| ΔS > 10 | 技术委员会评审 |

### 4.4 发布阶段：熵增风险分级

根据 delta-熵增大小对变更进行风险分级，采用不同的发布策略：

| 风险等级 | delta-熵增范围 | 发布策略 |
|---------|---------------|---------|
| 低风险 | ΔS ≤ 2 | 随时发布，自动部署 |
| 中风险 | 2 < ΔS ≤ 5 | 完整测试，灰度发布（10% 流量） |
| 高风险 | 5 < ΔS ≤ 10 | 全量测试，小流量逐步发布 |
| 极高风险 | ΔS > 10 | 禁止发布，重新设计 |

## 5. 长期熵增治理机制

### 5.1 熵增预算制度

这是控制长期熵增最有效的机制：

- **预算分配**: 每个团队每个迭代分配基础预算 `B_0 = 5 × N`（N 为团队人数）
- **预算使用**: 新功能开发消耗熵增预算，重构偿还技术债务释放熵增预算
- **预算结转**: 未使用的预算可结转至下一个迭代，但最多结转 50%
- **奖惩机制**: 熵增控制优秀的团队获得额外奖励预算，超标的团队扣减下一个迭代预算

### 5.2 技术债务量化与偿还

**技术债务量化标准**：

| 债务类型 | 熵增单位 |
|---------|---------|
| 循环依赖 | 10 / 个 |
| 上帝类（CBO > 20） | 50 / 个 |
| 低内聚类（LCOM3 > 0.7） | 20 / 个 |
| 重复代码 | 1 / 行 |
| 缺失文档 | 5 / 类 |

**偿还计划**：

- 每个迭代必须拿出至少 20% 的时间偿还技术债务
- 优先偿还熵增密度最高的技术债务
- 偿还技术债务释放的熵增预算可用于新功能开发

### 5.3 定期架构健康度审计

每 3-6 个月进行一次全面的架构健康度审计：

1. 计算整个系统的总熵值和各子系统的熵值
2. 绘制过去 6 个月的熵增趋势图，预测未来熵增
3. 识别熵增最快、熵值最高的热点模块
4. 评估系统存在的架构风险和潜在问题
5. 制定下一个周期的架构优化计划和熵增控制目标

### 5.4 认知熵增控制

- **文档标准化**: 建立统一的文档标准和模板，确保关键设计决策有记录
- **知识共享机制**: 定期进行代码分享、架构分享和技术培训
- **代码集体所有权**: 实行代码轮换制度，避免代码只有一个人能看懂
- **架构决策记录（ADR）**: 记录所有重要的架构决策及其理由

## 6. 本项目落地情况

### 6.1 当前实现（`complexity-score.sh`）

本项目通过 `.opencode/scripts/harness/complexity-score.sh` 脚本实现了**粗粒度的
delta-熵增评估**，在无 AST 解析器和 SonarQube 的条件下，基于 `git diff` + 路由索引
进行近似计算。

**实现的五维评分模型**：

```
ΔS = S_scale + S_coupling + S_spread + S_cycle + S_cognitive
```

| 维度 | 对应理论指标 | 脚本实现方式 | 上限 |
|------|-------------|-------------|------|
| **S_scale**（变更规模） | WMC 近似 | `行数变化/500 + 源码文件数/10` | 3.0 |
| **S_coupling**（耦合度） | CBO + RFC 近似 | 基于 call-graph.tsv 统计跨模块调用边数 / 5 | 3.0 |
| **S_spread**（扩散度） | 关联熵 S_coupling | `(涉及模块数 - 1) / 3` | 2.0 |
| **S_cycle**（循环依赖） | CYCLE | 基于 module-deps.tsv 检测双向依赖，每对 × 5 | 无上限 |
| **S_cognitive**（认知熵增） | 认知熵 | `新增文件占比 × 2` | 2.0 |

**风险分级与退出码**：

| ΔS 范围 | 风险等级 | 退出码 | 处理 |
|---------|---------|--------|------|
| ΔS ≤ 2 | 低风险 | 0 | 自动通过 |
| 2 < ΔS ≤ 5 | 中风险 | 0 | 通过，人工 CR 时重点关注 |
| 5 < ΔS ≤ 10 | 高风险 | 2 | 警告通过，需说明熵增理由 |
| ΔS > 10 | 极高风险 | 1 | 阻断，必须拆分变更 |

**脚本在流水线中的位置**: Verifier 阶段（阶段 5）的第一项验证，也在独立验证协议中作为 F1 执行。

### 6.2 理论体系 vs 脚本实现的差距

| 理论指标 | 脚本是否实现 | 差距说明 |
|---------|-------------|---------|
| CBO（对象间耦合度） | 近似 | 脚本通过 call-graph 统计跨模块边，非精确 CBO 计算 |
| RFC（类的响应集） | 未实现 | 需要 AST 解析 |
| CYCLE（循环依赖） | 已实现（模块级） | 仅检测模块级双向依赖，不含类级循环 |
| LCOM3（内聚缺乏度） | 未实现 | 需要 AST 解析字段访问关系 |
| WMC（加权方法数） | 近似 | 用行数变化粗略替代 |
| DIT（继承树深度） | 未实现 | 需要 AST 解析继承关系 |
| NOC（子类数量） | 未实现 | 需要 AST 解析 |
| 动态 delta-熵增 | 未实现 | 需要 APM 工具接入 |
| 熵增密度 ρ | 未实现 | 需要业务价值量化体系 |
| 系统健康度 H(t) | 未实现 | 需要长期熵值追踪基础设施 |

### 6.3 演进规划

**近期**（工具链完善）：

- 引入 SonarQube / MetricsReloaded 获取精确的 CK 度量指标
- 将脚本粗粒度评分替换为精确的 CBO / LCOM3 / WMC / DIT / NOC delta 计算
- 建立类级循环依赖检测（基于 symbol-table + call-graph 深化）

**中期**（流程深化）：

- 建立熵增密度评价体系，需先落地故事点/功能点估算规范
- 在 CI/CD 中硬性嵌入 delta-熵增门禁
- 建立系统健康度 H(t) 的周期性计算和趋势追踪

**远期**（运行时扩展）：

- 接入 APM 工具（SkyWalking 等）实现运行时耦合熵增度量
- 建立故障熵增 ΔS_f 和数据熵增 ΔS_d 的采集体系
- 实现完整的熵增预算制度和技术债务量化偿还机制

## 7. 实施指南

### 7.1 分阶段实施步骤

**第一阶段（1-2 周）：工具集成与基础配置**

- 安装 SonarQube、SonarLint、MetricsReloaded 等工具
- 配置指标阈值和检查规则
- 在 CI/CD 流水线中加入 delta-熵增检查

**第二阶段（2-4 周）：团队培训与试运行**

- 对团队进行体系培训，确保每个人理解指标含义和控制规则
- 选择一个非核心模块进行试运行
- 收集反馈，调整指标阈值和流程

**第三阶段（1-2 个月）：全面推广与制度建立**

- 在所有模块推广实施
- 建立熵增预算制度和技术债务偿还机制
- 将熵增指标纳入团队绩效考核

**第四阶段（长期）：持续优化与改进**

- 定期回顾体系运行效果
- 根据实际情况调整指标阈值和流程
- 逐步引入运行时熵增度量

### 7.2 常见问题与注意事项

- **避免过度度量**: 不要追求指标的绝对完美，重点关注 delta 值和趋势
- **区分必要和不必要熵增**: 不要为了降低熵增而牺牲业务功能
- **保持灵活性**: 根据项目特点和团队情况调整指标阈值和流程
- **避免唯指标论**: 指标是辅助工具，不能替代人的专业判断
